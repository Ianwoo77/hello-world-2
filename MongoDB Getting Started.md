# MongoDB Getting Started

- A *document* is the basic unit of data for MongoDB and is roughly equivalent to a row in a REL-DBS.
- A *collection* can be thought of as a table.
- A single instance of MongoDB can host multiple independent dbs, each of which contains its own collection.
- Each document has a special key `_id`. And that is unique within a collection.

Note that MongoDB is type-senenstive and case-sensitive. And MongoDB cannot contain duplicate keys.

### Collections

A *collection* is a group of documents. If a document is the mongodb analog of a row in a REL-DBS, then a collection can be thought of as the analog to a table.

#### Dynamic schemas

Collections have *dynamic schemas* -- documents within a single collection can have any number of different *shapes*. Cuz any document can be put into any collection -- 

- Keeping different kinds of documents in the same collection can be a nightmare for developers and admins.
- It’s much faster to get a list of collections than to extract a list of types of documents in a collection.
- Grouping documents of the same kind together in the same collection allows for data locality.

#### Naming

A collection is identified by its name. Collection names can be any UTF-8 string, with a few restrictions -- 

- The empty string is not a valid name
- Collection names may not contain character `\0`
- Should not create any collectoins with names that starts with `system`, a prefix reserved for internal collections.
- User-created collections should not contain the reversed character $ in their names.

#### SubCollections

One convention for organizing collections is to use namespaced sub-collections separated by the `.`character. Fore, an application containing a blog might have a collection named `blog.posts`and fore a separate collection named `blog.authors`-- and there is no REL between the *blog* collection and its *children*.

Although subcollections do not have any special properties, they are useful and are incorporated into many MDB tools.

### DBS

In addition to grouping documents by collection, MDB groups collections into *databases* -- A single instance of MDB can host several dbs -- each grouping together 0 or more collections. And there are same reserved dbs names. `admin, local config`.


`find`and `findOne`can be used to query a collection, if just want to see one document from a collection like:

### Data Types

Documents in MDB can be thought of as *JSON_like* in that they are conceptually similar to objects in Js. `Null, Boolean, Number, String, Date`And : 

- Regular expression -- `{‘x’: /foobar/i}`
- Array: `{‘x’: [‘a’, ‘b’, ‘c’]}`
- Embedded document like `{'x’: {“foo”, “bar”}}`
- Object ID fore: `{‘x’: ObjectId()}`-- 12-byte ID for documents
- Binary data -- is a string of arbitrary bytes, cannot be manipulated from the shell
- Code -- MDB also makes it possible to store arbitrary JS in queries and documents. FORE `{x: function(){...}}`

#### `_id`and `ObjectId`

Every document stored in MDB must have an `_id`key -- The `_id`'s value can’t be any type, but it defaults to an `ObjectId`. -- Is the default type -- is designed to be a lightweight, while stell being easy to generate in a globally unique way acorss different machines.

Autogenerated of `_id`-- If there is **no** `_id`presented when a document is inserted, one will be automatically added to the inserted document.

## Interface Pollution

An interface provides a way to specify the behavior of an object -- use interfaces to create common abstractons that multiple objects can implement. Makes Go interfaces so different is that they are satisfied implicitly. Fore, `io.Reader`and `io.Writer`-- 

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}
```

Fore, need to implement a func that should copy the content of one file to another like:

```go
func copySourceToDest(source io.Reader, dest io.Writer) error {...}
```

This func would work with `*os.File`parameters -- `*os.File`implements both `io.Reader`and `io.Writer`. Furthermore, writing a unit test for this function is easier like:

```go
func TestCopySourceToDest(t *testing.T) {
    const input = "foo"
    source := strings.NewReader(input) // Create an io.Reader
    dest := bytes.NewBuffer(make([]byte, 0)) // create an io.Writer
    err := copySourceToDest(source, dest)
    if err != nil {
        t.FatalNow()
    }
    got != dest.String()
    if got != input {
        t.Errorf("expected %s, got %s", input, got)
    }
}
```

Indeed, adding methods to an interface can decrease its level of reusability. Fore, `io.Reader`and `io.Writer`are powerful abstractions cuz they cannot get any simpler.

#### When to use interfaces

When should create -- Common behavior, decoupling, and restricting behavior. Fore:

```go
type Interface interface {
    Len() int
    Less(i, j int) bool
    Swap(i, j int)
}
```

Decoupling -- Another important is about decoupling our code from an implementation. If rely on an abstraction instead of a concrete imp, the imp itself can be replaced with another without even having to change our code. 

```go
type CustomerService struct {
    store mysql.Store // Depends on the concrete imp
}
func (cs CustomerService) CreateNewCustomer(id string) error {
    customer := Customer {id:id}
    return cs.store.StoreCustomer(customer)
}
```

If want to test this -- cuz `CustomerService`just relies on the actual imp to store a `Customer`-- we are obliged to test it through integration tests, which requires *spinning up* a MySQL instance. To give more flexibility, should *decouple* `CustomerService`from the actual imp -- which can be done via an interface like -- 

```go
type CustomerStorer interface {
    StoreCustomer(Customer) error
}
type CustomerService struct {
    storer CustomerStorer
}
func (cs CustomerService) CreateNewCustomer(id string) error {
    customer := Customer{id:id}
    return cs.storer.StoreCustomer(customer)
}
```

Cuz storing a customer is now down via an interface, this gives us more flexibility in how we want to test the method.

Restricting behavior -- Imagine implement a custom configuration package to deal with dynamic configuration -- create a specific container for `int`configuration via an `IntConfig`struct also exposes two methods like:

```go
type IntConfig struct {}
func (c *IntConfig) Get() int {
    //... retrieve some configs
}
func (c *IntConfig) Set(value int) {
    //... update some configs
}
```

For now, receive an `IntConfig`that holds some specific configuration, such as a threshold -- Are only interested in retrieving the config value want to prevent updating it. Semantically, this configuration is read-only, don’t want to change our configuration package -- like:

```go
type intConfigGetter interface {
    Get() int
}

// In the code, can realy on intConfigGetter instead the concrete imp
type Foo struct {
    threshold intConfigGetter
}
func New Foo(threhold intConfigGetter) Foo {
    return Foo {threhold: threhold}
}
func (f Foo) Bar() {
    threhold := f.threshold.Get()
    //... read the configuration
}
```

For this, the configuration getter is injected into the `NewFoo`factory method. It doesn’t impact a client of this function cuz it can still pass `IntConfig`struct as it implements `intConfigGetter`.

#### Interface Polllution

As discussed, interfaces are made to create abstraction -- main caveat when programming meets abstractions is remembering that abstractions *should be discovered, not created*. Means that we shouldn’t start creating abs in our code if there is no immediate reason to do so. We shouldn’t design with interfaces but wait for a concreted need.

### Multiple-record SQL queries

Finlly, look at the pattern for executing SQL statements which return multiple rows -- like:

```sql
SELECT id, title, content, created, expires from snippets
WHERE expires > UTC_TIMESTAMP() ORDER By id DESC LIMIT 10
```

```go
func (m *SnippetModel) Latest() ([]*Snippet, error) {
    stmt := `SELECT id... ORDER By id DESC LIMIT 10`
    rows, err := m.DB.Query(stmt)
    if err != nil {
        return nil, err
    }
    
    // defer calling rows.Close() to ensure the sql.Rows resultset is closed
    defer rows.Close()
    
    // initialize an empty slice
    snippets := []*Snippet{}
    for rows.Next() {
        s := &snippet{}
        err = rows.Scan(&s.ID, &s.Title, &s.Content, &s.Created, &s.Expires)
        if err != nil {
            return nil, err
        }
        // Append the slice
        snippets = append(snippets, s)
    }
    
    // When the rows.Next() loop has finished, we call the `rows.Err()` to 
    // retrieve any error that was encountered
    if err = rows.Err(); err != nil {
        return nil, err
    }
    return snippets, nil
}
```

### Transactions and other details

The `database/sql`package essentially provides a std interface between your Go app and the SQL dbs -- So long as use the `database/sql`package, the Go code you write will generally be portable and will work with any kind of SQL dbs. Fore, managing Null values -- can use a `sql.NulLString`type.

#### Wroking with transactions

It’s important to realize that calls to `Exec, Query...`can use *any connection* from the `sql.DB` -- Even if you have two calls to `Exec()`immediately next to each other in your code, there is no guarantee that they will use the same dbs connection -- sometimes it’s not acceptable. To guarantee that the same connections is used can wrap multiple statement in a *transaction* like:

```go
type ExampleModel struct {
    DB *sql.DB
}

func (m *ExampleModel) ExampleTransaction() error {
    tx, err := m.DB.Begin()
    if err != nil {
        return err
    }
    defer tx.RollBack() // if succeeds, no-op, otherwise rollback
    _ err = tx.Exec("INSERT INTO...")
    if err != nil {
        return err
    }
    
    _, err = tx.Exec("UPDATE ...")
    if err != nil {
        return err
    }
    
    //...
    // if there is no errors, committed to the dbs with the tx.Commit()
    err = tx.commit()
    return err
}
```

#### Prepared Statements

The `Exec()`... methods all use prepared statements behind the scenes to help prevent SQL injection attacks. They set up a prepared statement on the dbs connection -- run it with the parameters provided, and then close the prepared statement. A better approach could be make use of the `DB.Prepare()`method to create our own prepared statement once, and reuse instead -- This is particularly true for complex SQL statements. 

```go
type ExampleModel struct {
    DB *sql.DB
    InsertStmt *sql.Stmt
}

func NewExampleModel(db *sql.DB) (*ExampleModel, error) {
    insertStmt, err := db.Prepare("INSERT INTO...")
    if err != nil {
        return nil, err
    }
    return &ExampleMOdel{db, insertStmt}, nil
}

func (m *ExampleModel) Insert(args...) error {
    _, err := m.InsertStmt.Exec(args...)
    return err
}

func main(){
    db, err := sql.Open(...)
    if err != nil {
        errorLog.Fatal(err)
    }
    defer db.Close()

    if err != nil {
        errLog.Fatal(err)
    }
    defer exampleModel.InsertStmt.Close()
}
```

### Dynamic HTML templates

- Pass dynamic data to your HTML templates in a simple, scalable and type-safe way.
- Use the various actions and function in Go’s html/template package to control the display of dynamic data
- Create a template cache so that your templates aren’t being read from disk for each HTTP
- Gracefully handle template rendering errors at runtime.
- Implement a pattern for passing common dynamic data to web pages without repeating code
- Create own custom functions to format and display data in HTML templates. Fore:

