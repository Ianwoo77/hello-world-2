### Tuples as Immutable lists

The py interpreter and stdlib make extensive use of tuples as immutable lists, and so should U -- Performance -- A `tuple`uses less memory than a `list`of the same length -- it allows Py to do some optimizations. However, just be aware that the immutability of a `tuple`only applies to the references contained in it. Namely, when the last item in `b`is changed b and a different. Note that tuples mutable items can be a source of bugs. If you want to determine explicitly if a tuple has a fixed value, can use the `hash`built-in to create `fixed`functin like this:

```py

        hash(o)
    except TypeError:
        return False
    return True

tm = (10, 'alpha', [1,2])

```

- To evaluate a tuple literal, the py compiler generates bytecode for a tuple constant in one operation, but for a list literal, the generated bytecode pushes each element as a separate to the data stack
- Given a tuple `t`, `tuple(t)`simply returns a reference to the same `t`. -- there is no need copy -- in contrast, `list(l)`will create a copy of `l`.
- Cuz of its fixed length, a `tuple`instance is allocated the exact memory space it needs. Instances of `list`-- are alocated with room to spare.
- The references to the items in a tuple are stored in an array in the tuple struct -- while just a list holds a pointer to an array of references stored elsewhere.

### Pattern Matching with Seqs

The most visible new feature in Py 3.10 is pattern matching with the `match/case`statement like:

```py
def handle_command(self, message):
    match message:
        case ['BEEPER', frequency, times]:
            self.beep(times, frequency)
        case ['NECK', angle]:
            self.rotate_neck(angle)
        case _:
            raise TypeError(message)
```

1. The expression after the `match`keyword is the *subject*-- the subject is the data that py will try to match to the patterns in each `case`clause
2. This pattern matches any subject this is a sequence -- the first must be string `BEEPER`, second and third may be anything.
3. If the number of items doesn't match, Py proceeds to the next `case`.
4. For the `_`, just match any subject that did not match a previous pattern.

On the surface, `match/case`may be same from the C and other langs -- but -- one key improvement of `match`over `switch`is **destructuring** -- a more advanced from of unpacking -- Destrucuring is a new word -- like:

```py
def main():
    print(f'{"":15} | {"latitude":>9} | {"longitude":>9}')
    for record in metro_areas:
        match record:
            case [name, _, _, (lat, lon)] if lon <= 0:
                print(f'{name:15} | {lat:9.4f} | {lon:9.4f}')

main()
```

For this:

1. The subject of this `match`is `record`-- each of tuples in `metro_areas`
2. A `case`clause has two parts, a pattern and an optional guard with the `if`keyword.

In general, a sequence pattern matches the subject if:

1. The subject is a sequence *and*:
2. The subject and pattern have the same number of items *and*:
3. Each corresponding item matches, including nested items

Sequence patterns may be written as tuples or lists or any combination of nested tuples and lists, but it makes no difference which syntax you use -- in a sequence pattern, square brackets and parentheses mean the same thing.

A sequence pattern can match instances of most actual or vritual subclasses of `collections.abc.Sequence`. FORE

```py
match tuple(phone):
    case ['1', *rest]: #...
    case ['2', *rest]: #...
    case ['3' | '4', *rest] #...
```

The `_`symbol is special in patterns -- it matches any single item in that position. But it is never bound to the value of the matched item.

And, can make patterns more specific by adding type information -- fore, the following matches the same nested sequence structure as the previous example. like:

`case [str(naem), _, _, (float(lat), float(lon))]:`

On the other hand, if you want to match any subject sequence starting with a `str`and ending with a nested seq:

`case [str(name), *_,  (float(lat), float(lon))]`

`str`indicates `name`must be a string, and lat must be `float`...

And the `*_`matches any number of items, without binding them to a variable. The optional guard clause starting with `if`is evaluated only if the pattern  matches, and can reference varaible bound in pattern like:

```py
match record:
    case [name, _, _, (lat, lon)] if lon <=0:
```

Underlying the way mapping deal with missing key is the aptly named `__missing__`method -- is not defined in base `dict`class, but `dict`aware of it -- if your subclass dict and provide a `__missing__`method, the STD `dict.__getitem__`will call it whenever a key is not found, instead of raising `KeyError`.

```py

        try:
            return self[key]
        except KeyError:
            return default

    def __contains__(self, item):
        return item in self.keys() or str(item) in self.keys()
```

## Interfaces

In Ts, object types are a way to describe object shapes, and also includes an `interface`feature many developers prefer -- Interfaces are another way to decalre an object shape with an associated name -- Interfaces are in many ways just similar to aliased object types but are generally preferred for their more readable error messages. for aliased object type like:

```tsx
type poet = {
    born: number;
    name: string;
};
// equivalent syntax for an interface
interface Poet {
    born: number;
    name: string;
}
// these two are almost identical
```

Ts' assignability checking and error messages for interfaces also work and look just about the same as they do for object types fore:

```tsx
interface Poet{
    born: number;
    name: string;
}

let valueLater: Poet;

valueLater = {
    born: 1935, name: 'Sara Teasdale',
};
```

However, there are a few differences betwen interfaces and type aliases -- 

- Interfaces can *merge* together to be augmented
- Interfaces can be used to type check the structure of class declartions while type aliases cannot.
- Interfaces are generally speedier for the Ts type checker to work with. They declare a named type that can be cached more easily internally, rather than a dynamic copy-and-paste of new object literal the way type aliases do.
- Cuz interfaces are considered named objects rather than an alias for an unnamed object literal. Their error messages are more likely to be readable in hard edge cases.

### Type of Properties

Js objects can be wild and wacky in real-world usage, including getters and setters, properties that only sometimes exist, or accepting any arbitrary property names and, Ts provides a set of type system tools for interfaces to help us model that wackiness.

Optional properties -- As with object types, interface properties don't all have to be rquired in the object, can like:

```tsx
interface Book {
    author?: string;
    pages: number;
}

const ok: Book = {pages:80}
```

### Read-only properties

May sometimes wish to block users of your interface from reassigning properties of objecs adhering to an interface. Ts allows you to add a `readonly`modifier before a property name to indicate that once set, the prop should not be set to a different value fore the `text`property in the below `Page`interface gives back a `string`when accessed.

```tsx
interface Page {
    readonly text: string;
}

function read(page: Page) {
    console.log(page.text); //ok
    page.text += '!'; // error
}
```

Note that the `readonly`exist only in the type system, and only apply to the usage of that interface -- won't apply to an object unless that object is used in a location that declares it to be of that interface. Declaring the variable with the explicit type annotation `:Page`would have indicated to Ts that its text was just `readonly`.

### Functions and Methods

Very common in Js for object members to be a function -- Ts therefore allows declaring interface members as being the function types previously -- provides two wasy of declaring interface members as functions like:

- Method syntax -- declaring that a member of the interface is a function intended to be called as a member of the object like `member():void`
- Property syntax -- declaring that a member of the interface is equal to a standalone function like: `member: ()=>void`.

The two forms are an analog -- Both `method`and `property`members shown are functions that may be called with no parameters and returns a `string`.like:

```tsx
interface HasBothFunctionTypes {
    property: () => string;
    method(): string;
}

const hasBoth: HasBothFunctionTypes = {
    property: () => "",
    method() {
        return '';
    }
}
```

Both forms can receive the `?`optional modifier to indicate they dont need to be provided like:

```tsx
interface OptionalReadonlyFunctions {
    optionalProp? : ()=> string;
    optionalMethod?():string;
}
```

Main difference -- 

- Methods cannot be decalred as `readonly`, props can be.
- Interface merging treats them differently.
- Some of the operations performed on types treat them just differently.
